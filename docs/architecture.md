# Architecture

Proof is split into a platform-neutral engine package, `ProofKit`, a shared app layer, `ProofUI`, and thin app targets on top of them. The Mac app comes first; an iPad and iPhone app reuses `ProofKit` unchanged and shares `ProofUI` with the Mac.

Thumbnails and look previews are `CGImage`, which SwiftUI draws on both platforms.

The Mac app runs in the App Sandbox. Its project links `ProofKit` and `ProofUI` as a local Swift package, so a change to either is picked up by the next app build without a version bump. The version and build number are set in `App/Version.xcconfig`. The iOS app is a second target in the same project, for iPad and iPhone, with the same bundle identifier, version, icon and accent color. Since [decision 0051](decisions/0051-mobile-workflow.md), iPad and iPhone serve a mobile workflow of culling, quick edits and sharing, and get a Mac feature only when it fits that workflow. From the filmstrip in Edit, the sheet presents from the inspector's sheet while that is up on iPhone, as History does. ## Render pipeline

Every render starts from the original RAW file and applies the edit recipe in this order:

1. RAW decode in linear light with `CIRAWFilter`: exposure, white balance (temperature and tint), sharpening and noise reduction (decision 0016), lens corrections, then perspective (decision 0025), then spot removal (decision 0039), then halation and bloom (decision 0028)
2. Tone: highlights and shadows, then texture and clarity, then dehaze, then contrast, whites, blacks and the tone curve baked together into one lookup per channel
3. Layers: each layer's adjustments, blended in by its mask, in order (decision 0040)
4. Color: vibrance, saturation, selective color, black and white
5. LUT, applied with `CIColorCubeWithColorSpace` in display-referred Rec.709/sRGB and blended by strength
6. Quarter turns and flips, then straighten and crop
7. Vignette, then grain, on the cropped frame, and the output transform to the display or export color space

`RAWRenderer` in `ProofKit` builds this graph from an `EditRecipe` in one function, `RAWRenderer.apply`, which the canvas and the thumbnails both use. It applies every step. The decode uses the recipe's color profile: Apple's, through Core Image's default decoder, or the one a DNG carries, through the newest `.dng` decoder version that gives an image (in the iOS 27 simulator `9.dng` gives none for the Leica M11, so `8.dng` is used; decision 0053), offered only where Core Image applies all of it (`CameraProfiles`; see `docs/decisions/0044-camera-profile.md`). The renderer sets the decoder before working out the scale, since the embedded profile's frame can be a few pixels larger, and keeps each profile's size and defaults from when the photo opened, because the `.dng` decoders report a size already scaled. Then white balance, through `CIRAWFilter.neutralTemperature` and `neutralTint`, and exposure, in stops, through `CIRAWFilter.exposure`. Highlights and shadows follow the decode, in linear light, through a custom Metal kernel compiled when it is first used (see `docs/decisions/0009-highlights-shadows.md`); with both at 0 the stage is skipped. Texture and clarity follow, also in linear light, through a third kernel that compares each pixel's brightness with a small blur (texture) and with an edge-aware map of its area (clarity) and scales the difference (see `docs/decisions/0017-texture-clarity.md`); with both at 0 it is skipped. Dehaze follows, through kernels that measure haze on a small map of the photo with the dark-channel prior, estimate the haze's color, and remove or add haze following the photo's edges (see `docs/decisions/0020-dehaze.md`); at 0 it is skipped. Contrast, whites, blacks and the tone curve follow as one lookup per channel, applied by a second kernel (see `docs/decisions/0010-tone-lookup.md` and `0011-tone-curve.md`); with the three sliders at 0 and every curve straight it is skipped too. Layers follow, on the whole uncropped photo: each enabled layer runs its own adjustments through the same tone stages and `ColorAdjustments`, with temperature, tint and exposure as one channel scale, then a kernel blends the result in by the layer's mask. Gradients are generator kernels; a brush mask is drawn on the CPU at 2048 pixels and cached (`BrushRaster`); a subject mask is a PNG Vision made when it was added, kept in the recipe (see `docs/decisions/0040-masks.md`). Without layers the stage is skipped. While the Masks tool shows a mask, the canvas's recipe names it in `maskOverlay`, and the renderer tints it red after the look and before the crop. Vibrance and saturation follow, still in linear light: vibrance through `CIVibrance`, which raises muted colors more than vivid ones and leaves grays alone, then saturation through `CIColorControls`, which changes all colors alike; each filter is skipped while its slider is at 0. Because they work in linear light, equal slider steps don't look equally large across the range. A perceptually even version would change how saved edits render, so it would come with a `processVersion` bump. Selective color follows, through one more kernel that finds each pixel's hue, weighs it between the two nearest of eight color ranges, and turns its hue, scales its saturation and changes its brightness by those ranges' values, fading out toward gray (see `docs/decisions/0026-selective-color.md`); with every range at 0 it is skipped. The black-and-white mix follows, through `CIColorMatrix`, which sets every channel to the same weighted blend of red, green and blue (see `docs/decisions/0027-black-and-white.md`); while the treatment is Color it is skipped. The histogram measured from each canvas render also counts the photo's hues, for the Selective Color card's graph; while the photo is black and white, the hues are counted in a small copy rendered without the mix, so the graph keeps showing the colors Selective Color adjusts. The LUT stage converts the image from the linear working space to sRGB, looks each color up in the LUT with `CIColorCube`, blends the result with the image before the LUT by strength, still in sRGB, and converts back (see `docs/decisions/0013-applying-luts.md`). Strength runs from 0 to 1 and is clamped; at 0, or with no LUT loaded, the stage is skipped, so the photo renders exactly as with no look. The geometry stage turns and flips the photo, then turns it by the straighten angle around the crop rectangle's center and keeps only the rectangle, in whole pixels; the photo is clamped at its edges first, so a rectangle that touches them doesn't blend with nothing. The vignette follows, through one more kernel that darkens or lightens each pixel by its distance from the cropped frame's center, so it follows any crop and a zoomed region matches the whole frame (see `docs/decisions/0021-vignette.md`); with Amount at 0 it is skipped. Grain follows, through one more kernel that adds value noise sized relative to the cropped frame; below full resolution each pixel shows the average of the grains it covers, so the canvas shows the grain an export shrunk to the same size would have (decision 0028). With Amount at 0 it is skipped. The scale a render is decoded at fits the cropped photo, not the whole one, to the target size. Sharpening and noise reduction are set on the same filter; `null` values keep the camera's defaults, and the decoder sharpens only above half size. The lens profile is set there too, through `CIRAWFilter.isLensCorrectionEnabled`, and only for files where `isLensCorrectionSupported` is true; other files, such as Leica M DNGs, which carry no correction data, are left alone. An edit without its own setting keeps the decoder's default. Chromatic aberration is corrected right after the decode, by a kernel that reads red and blue at the scales the edit stores, about the photo's center; Proof measures those scales from the photo when Remove Chromatic Aberration is turned on (see `docs/decisions/0023-chromatic-aberration.md`). Manual lens vignetting and distortion follow, for lenses without a profile, still about the uncropped photo's center: one kernel scales each pixel like exposure by its distance from the center, and another reads each pixel from a radius scaled by a one-term radial model, with the photo enlarged just enough to fill the frame (see `docs/decisions/0024-manual-lens-corrections.md`). Each is skipped at 0. Perspective follows, through `CIPerspectiveTransform`, still on the whole photo as the camera oriented it, so it comes before the crop's turns and stays with the photo when it is turned: the four corners go where a homography for the Transform sliders puts them, enlarged to fill the frame while Constrain Crop is on (see `docs/decisions/0025-perspective.md`). It is skipped while the sliders are neutral. Halation and bloom follow, still on the whole photo, so light from outside the crop spreads into it: one kernel keeps the highlights of a 2048-pixel copy of the photo, counting lights near the clip point as up to 4 stops brighter unless their surroundings are bright too; the result is shrunk to a 1024-pixel map, which is cached, and blurred by a share of the photo's long edge, and another kernel adds what spills past each pixel's own highlights, mostly in red for halation and in every color for bloom (see `docs/decisions/0028-effects.md`). With both Amounts at 0 the stage is skipped. Upright finds straight segments in a 1024-pixel render of the uncorrected photo (`LineDetector`) and solves for the sliders (`Upright`), both in `ProofKit`. The renderer reads the camera's white balance (As Shot), its default sharpening and noise reduction, and whether it has a lens profile and applies it by default when it opens a photo, because it reuses one filter across renders and has to put those values back when an edit returns to them. Auto white balance and Auto Tone measure a render of about 256 pixels with the same function and write ordinary slider values to the edit; the white balance is found by rendering a few candidates (see `docs/decisions/0018-auto-adjust.md`). The white balance eyedropper uses the same search but measures only a small patch around the click, rendered on its own (see `docs/decisions/0019-white-balance-eyedropper.md`). The other stages pass the image through until their controls are built. It is an actor, so decoding and GPU work run off the main thread. It opens a file once and renders it into a Metal texture scaled to fit a requested pixel size. Its `CIContext` caches intermediate results, so after the first render at a given size, a change to a later stage such as exposure reuses the decoded RAW data instead of decoding it again. Opening another photo clears the cache, so GPU memory holds the intermediates of one photo at a time. Cached and uncached renders of the same settings produce the same pixels. Each app's canvas is an `MTKView` that draws the latest texture scaled to the view, through the shared `PhotoCanvasCoordinator`; on resize it keeps drawing the old texture until a render at the new size finishes. The canvas runs one render at a time and never discards one in flight: while a slider is dragged faster than renders finish, each finished render is shown and the next starts from the slider's latest value. A photo opened in Edit, or stepped to in the filmstrip, shows its cached thumbnail at once while its first render runs: the thumbnail of its current edit, which the grid and the filmstrip show too, so it already has the edit's crop and colors. It is looked up with `ThumbnailCache.cachedThumbnail(for:edit:)`, which never renders, and drawn by `RAWRenderer.placeholder` into the frame of the cropped photo's full size. That size is read from the file's header with ImageIO, which on a NAS takes about 7 ms where opening the file with `CIRAWFilter` takes 110–340 ms; for the Leica DNGs checked, both give the same size, and a test compares it with a render's on the sample photo. That is the frame the render fills, so the render replaces the thumbnail without moving the photo, even when the thumbnail's own shape differs slightly. A photo without a cached thumbnail shows a small progress indicator where it will appear until its render is ready. The canvas draws, and makes these placeholders, with a Core Image context and command queue of its own, so a new photo's thumbnail never waits behind the decode of the photo before it; with the shared context, the previous photo stayed on screen under the new photo's name until its decode finished. A render can't be stopped once it starts, so a render for a photo that is no longer shown is dropped before each step that can be skipped: before the file is opened and before the photo is rendered. While stepping quickly, at most the one render already in flight finishes, and the next one starts from the photo shown then. Errors from a photo no longer shown aren't reported.

`CubeLUT` in `ProofKit` reads 1D and 3D `.cube` files into a table of colors with its input domain, and reports malformed files with an error that names the line (see `docs/decisions/0012-cube-parser.md`). `PreparedLUT` lays a `CubeLUT` out as the 3D lattice over 0 to 1 that Core Image takes, once per LUT, and the renderer takes it next to the recipe. `LUTLibrary` finds the file `look.lut` names and prepares it (see the LUT library section below). 1D tables are sampled onto a 65-per-side lattice, tables with another domain onto 0 to 1, and tables larger than 128 per side, the most Core Image accepts, down to 128.

A render request always carries a target size. Interactive renders are always at the window's full size, including while a slider is dragged, so the photo never turns soft and a change to detail, such as Clarity, can be judged as it is made. With the decode cached, an exposure change renders at a full-screen size in 2–16 ms (median) on an M2 with a 60 MP DNG, inside one 30 fps frame. If a later stage is too slow for that, it is made faster rather than rendered at a reduced size. Only export renders at full sensor resolution.

Zoom renders only what the view shows. `Viewport` in `ProofKit` holds the zoom, as screen pixels per photo pixel or Fit, and the photo point at the view's center; it gives the photo's frame in the view, with its origin in whole pixels so that 100% puts one photo pixel on one screen pixel, and the part of the photo that is visible. While the view shows the photo larger than the screen-size render, the canvas asks `RAWRenderer.render(region:scale:)` for the visible part, plus an eighth of the view past each edge, at the view's scale up to full resolution. The region is cropped from the same graph after the geometry stage, so Core Image computes only that part, and its pixels are the same as that part of a full-resolution render (a test checks this on the sample photo). Past 100% the region is rendered at full resolution and enlarged on screen, nearest pixel first, so pixels stay crisp. The canvas draws the screen-size render, enlarged, under the region, so a pan moves at once and the edges it uncovers show soft until the next region is ready. While zoomed, the region renders before the screen-size photo, which then catches up for the histogram and for those edges. On an M2 with the 60 MP sample in a 2560×1600 view at 100%, a region of the view alone renders in about 49 ms (median), a region with the margin in about 81 ms, and an exposure change on a region in about 4 ms.

On iPhone and iPad a large photo's memory is kept within what iOS allows (see [decision 0053](decisions/0053-memory-on-iphone.md)). The photo at Fit renders at the canvas's size as on the Mac. A zoomed region is cut from the whole photo decoded at the zoom's scale, so `RenderBudget` in `ProofKit` limits that scale: half the memory `os_proc_available_memory` reports, a quarter under serious or critical thermal pressure, at 64 bytes per decoded pixel. `PhotoCanvasCoordinator` reads it when a photo opens and after a memory warning, and past the scale it allows the region is enlarged smoothly. On the Mac there is no limit. The iOS canvas calls `PhotoCanvasCoordinator.releaseMemory()`, which clears the renderer's cached decode (`RAWRenderer.clearCaches()`), when memory runs low, when the app goes to the background and when Edit ends. On an M2 with the 60 MP sample and its saved edit, opening and editing at an iPhone canvas's size (1206×1300 pixels) peaks at about 1.1 GB, with an exposure change in about 34 ms (median); a region at 50%, 70% and 100% peaks at about 1.8, 2.6 and 3.2 GB. In the iPhone 18 Pro simulator, which runs the GPU in software and leaves GPU memory out of the footprint, the same exposure change takes about 226 ms. Numbers from an iPhone are still to be measured (#238).

### Edits

`Sidecar` in `ProofKit` reads and writes a photo's `.proof` file with `NSFileCoordinator`. It keeps the JSON it read, so saving keeps fields this version doesn't recognize. Saving the recipe the photo opens with deletes the file instead, unless it has unrecognized fields; a photo with no sidecar and that edit gets no file (decision 0007). For most photos that recipe is neutral. A photo whose camera saved a crop or perspective correction in the file opens with them, read by `CameraSettings` in `ProofKit` from the DNG `DefaultUserCrop` tag and Leica's perspective-control XMP (decision 0035); `PhotoEdit.cameraEdit` holds it. Revert to Original deletes the file whatever it holds, as one undo step; undoing it saves the edit as a new file. The first save also stores the original's `OriginalFingerprint`: its size, capture time and unique image ID. When `Library` reads a folder it can write to, `Sidecar.relink(in:)` first renames sidecars left behind by a renamed photo to that photo, when exactly one photo without a sidecar has the same fingerprint; only photos of the same size are opened to compare. When a folder is read again, because FSEvents reported a change or, on a network volume, because Proof became active or View › Reload Folders was chosen, each photo in it with an edit in memory has its sidecar read; if it differs from what Proof last read or wrote, the edit on disk becomes the current edit as one undo step named "Changed Elsewhere". Proof's own writes match what it last wrote, so they change nothing. A photo with a change in progress or an edit that couldn't be saved keeps its edit (decision 0007).

When a photo is first opened in Edit, `Library` reads its sidecar into a `PhotoEdit`, which holds the recipe the controls show and an `EditHistory`. Each undo step is a whole recipe. A slider drag becomes one step when it ends; a change made without a drag, such as a double-click reset, becomes one once the controls have been idle for 0.4 seconds. Each step is saved as soon as it is made. Each photo keeps its edit and undo history in memory until Proof quits, so returning to a photo still allows undo. Edit › Undo and Redo (⌘Z, ⇧⌘Z) apply to the photo open in Edit.

The History panel (View › Show History, ⌘Y, or the clock button beside the filmstrip's) lists the same steps in Edit's leading column, where Browse has the folders: newest first, with Original, the photo without an edit, at the bottom, and Opened above it when the photo already had an edit (#56). Original is there even after Proof restarts, so Undo can always return to it. Each step is named by `EditRecipe.changeLabel` in `ProofKit`: one Basic or white balance slider names itself and its value, as the slider shows it ("Exposure +0.30", "Temperature 5600"); other changes name their card or section, such as Curve or Vignette; a change across several is Several Adjustments. Paste Settings, Revert, Auto Tone and Reset Basic are named as such. Clicking a step shows the photo as it was then and saves that edit; Undo and Redo move on from there, and steps after it are dimmed until a new change drops them. The history is not saved with the edit; it lasts until Proof quits, as undo does.

Edit › Copy (⌘C) opens a sheet with checkboxes in three columns grouped by inspector card: each card has a checkbox, which shows a dash while only some of its items are ticked, over one for each slider or section on it, such as Exposure, Treatment, Noise Reduction, Remove Chromatic Aberration or Grain. Cards with one control, such as Curve and Look, are a single checkbox; Profile, which sits in the Histogram card, heads the first column; and Crop, Spot Removal and Masks sit beside Transform. Both the Mac's columns and the iOS list follow `SettingsItem.sheetGroups`. All but Transform and Crop start ticked, since they fit the photo they came from and suit others only when nothing moved, as on a tripod; the ticks are remembered. Copy works in Browse too, from the selected photo, or from the one with the stronger outline when several are selected. Edit › Paste (⌘V) replaces those items of every selected photo with the copied values, in Browse or Edit, as one undo step in each photo's own history that is saved like any other; each card with a pasted item takes the copied photo's switch, so the pasted settings render as they did there. A photo that hasn't been opened in Edit has its sidecar read first. Transform comes across whole, its guides and Upright mode included. Crop copies the rectangle with the turns, flips, straighten angle and ratio, because the rectangle lies in the photo as turned and flipped. What is copied stays in memory until Proof quits; nothing goes to the system pasteboard. While a field is being typed in, ⌘C and ⌘V copy and paste its text instead; Copy Settings… and Paste Settings in the same menu always act on settings. `SettingsItem` and `EditRecipe.pasting` in `ProofKit` decide what each item covers.

Before writing, `Library` checks `ensureCanWrite(nextTo:)`. If the folder hasn't been granted again for writing, the folder picker opens once per folder per session, and the change stays in memory with a note in the inspector, which offers Grant Access…. Edits waiting on that folder are saved once it is granted. A photo saved on its own by an early build is granted through its folder the same way (decision 0008). A sidecar that can't be read is never written over. Sidecars are read and written on the main thread; they are small, but a slow network volume can delay a save.

### LUT library

`LUTLibrary` in `ProofKit` keeps the person's LUTs as `.cube` files in `Application Support/Proof/LUTs`, inside Proof's own container, and `look.lut` names one by its path there, such as `Portra/400.cube` (decision 0014). Proof ships with none. Add Looks… in the Looks section's folder pop-up, or a drop on its list, imports `.cube` files and folders; a folder keeps its name and subfolders, and other files in it are left out. Each file is parsed first; one the parser refuses isn't copied, and the parser's message is shown. A file whose name is taken in its folder by one with other contents is numbered, as in "Portra 2.cube", so a LUT an edit names never changes. The library is an actor: each LUT is read and prepared once, off the main thread, and kept prepared up to 512 MB, letting the least recently used go first. The canvas, edited thumbnails and Auto straighten all ask it for the LUT a recipe names, so switching between looks that have been previewed renders at the speed of any other change. A LUT that isn't in the library is skipped, and the Looks section says so.

The Looks section shows one folder of the library at a time, chosen from a full-width pop-up button titled with the chosen look, whose folders with subfolders open as submenus, and shows that folder's LUTs three across as previews of the photo in Edit through each. The photo is rendered once, 160 pixels on the long edge, with its edit but no look, and each LUT is applied to that small image, so the RAW file is decoded once for all previews. The previews are kept until the photo or the rest of its edit changes, and are made again a quarter second after a change rests. With the grid focused, the arrow keys move between tiles and choose as they go; Photo › Next Look and Previous Look step through the shown folder from anywhere in Edit. Proof reads the library's folder again whenever it becomes active, so changes made in the Finder through Reveal in Finder appear.

### Export

File › Export… (⇧⌘E) and the right-click menu open `ExportSheet` for the selected photos: format, size, color space and Remove Location, remembered between exports as `ExportSettings`. `ExportQueue` in the app exports one photo at a time in the background with a `RAWRenderer` of its own. `RAWRenderer.export` decodes the file at the scale that fits the size asked for and applies the same graph as the canvas, then makes the size exact and renders into a bitmap without alpha, 16 bits per channel for TIFF. It decodes at exactly full size when the fitted scale is within a pixel of it, and renders into a texture with a Core Image context of its own that caches intermediates, at low GPU priority so the canvas's renders go first. On an M11 DNG with clarity, dehaze, highlights and shadows, a curve and a crop, a full-size JPEG export takes about 8 s, as long as the canvas's first full-size render (see [decision 0043](decisions/0043-export-speed.md)). The export context frees its cached intermediates when each export ends. A photo wider or taller than the device's largest texture, 16384 pixels on a Mac, iPad or iPhone and 8192 in the iOS simulator, renders in tiles that share the whole-photo maps through that cache (decision 0053). `PhotoExport` writes it with ImageIO, with the original's Exif, TIFF and GPS properties and the rating and description as IPTC and XMP, next to any file of the same name rather than over it. Each photo is exported with its edit as it was when Export was clicked. Once Export is clicked, and for File › Export To, the sheet shows the export's progress and Stop Export, then a summary, until Done. See [decision 0031](decisions/0031-export.md). Saved destinations, a folder and settings under a name, are kept by `ExportDestinations` in `ProofKit`, with their folder grants made and resolved by `FileAccess`. The sheet's Export To picker and File › Export To export to one without an open panel. See [decision 0032](decisions/0032-export-destinations.md).

On iPad and iPhone, the Share button in Edit's toolbar and in the selection's bottom toolbar, and Export… in the touch-and-hold menu, open the app's `ExportSheet`: Share…, Save to Files… and Save to Photos above the same choices as the Mac's, from `ExportSettingsForm` in `ProofUI`, which both apps' sheets use. The settings are remembered as `ExportSettings.remembered`. Export To in the touch-and-hold menu lists the same three destinations and exports with the remembered settings. `ExportQueue.start(_:settings:delivery:)` renders with the same `PhotoExport` into a temporary folder (`ExportStaging` in `ProofKit`), then the sheet opens the share sheet or Save to Files (`fileMover`) once every photo is ready; Save to Photos adds each photo as it is ready through add-only Photos access (`PhotoLibrary` in `ProofUI`). Done removes the folder. While the app is in the background, where iOS gives it no GPU, the queue waits between photos (`PauseGate`), and a photo whose render failed because the app left the foreground goes back in the queue. See [decision 0052](decisions/0052-export-on-ios.md).

### Thumbnails

`ThumbnailCache` in `ProofKit` makes and stores thumbnails, 512 pixels on the long edge, as JPEG files in `Application Support/Proof/Thumbnails` on the Mac and in `Caches/Proof/Thumbnails` on iPad and iPhone, which iOS doesn't back up and can clear. A thumbnail comes from the JPEG preview that the camera or DNG converter embedded in the RAW file, so the RAW data isn't decoded. Only a file without an embedded preview is decoded in full.

Each photo has a folder in the cache named from a hash of its path, and the thumbnail inside is named from a hash of the file's size and modification date. A file whose size or date changed misses the cache, and storing its new thumbnail removes the old one. The size and date are read from the file system on every lookup, because a `URL` keeps resource values it has already read. The cache has a size limit, 500 MB on iOS and 2 GB on the Mac. Reading a stored thumbnail sets its file's modification date, and when the cache passes the limit the photo folders read least recently are removed until it is under 90% of it, so thumbnails of photos that were deleted or moved go first. The first thumbnail stored after launch measures the cache; after that Proof keeps a running estimate and measures again only when the estimate passes the limit (see [decision 0057](decisions/0057-thumbnail-cache-limit.md)). The cache can be deleted at any time.

An edited photo's thumbnail is rendered from the RAW file with its edit instead, by a `RAWRenderer` of its own, so it matches the photo in Edit and never delays the canvas. Its cache file is also named from the edit, and from the version of the LUT the edit's look names, so a changed edit or LUT misses the cache; a look whose LUT is missing is left out, as on the canvas. When a folder is listed, the sidecars of photos marked as edited are read to find their edits; on a NAS that is one extra read per edited photo, and rendering an edited thumbnail the first time is slower than reading an embedded preview. After each change in Edit, `Library` renders the photo's thumbnail again and the grid and the filmstrip show it in place of the one they loaded. The canvas shows the same cached thumbnail while a photo's first render runs (see the render pipeline above). An unedited photo with camera settings (decision 0035) is rendered with them the same way, under the cache name of an unedited photo, so the grid shows it as Edit opens it; an edit that changes only the crop and perspective has the file's metadata read to see whether it is that one.

For a folder, cached thumbnails arrive first, then the missing ones are made four at a time so a NAS isn't asked for the whole folder at once. A file that can't be read arrives without an image and doesn't stop the rest.

## Window layout

The Mac app has one window. Panels sit beside the photo and never cover it; see [decision 0004](decisions/0004-window-layout.md).

- The sidebar is a `NavigationSplitView` sidebar listing the saved folders. Each one expands into its subfolders exactly as they are on disk; Proof doesn't group or reorganize them. Each row shows how many photos sit directly in that folder. Proof lists RAW, JPEG and HEIC files, not PNG or TIFF; a RAW comes before a JPEG or HEIC of the same name. JPEG and HEIC photos can be browsed and rated but not yet edited or exported (#239); see [decision 0049](decisions/0049-jpeg-heic-sidecars-and-stacks.md). A folder is read with `FolderContents.read` off the main thread when its row first appears, so a tree on a NAS costs one directory listing per visible folder.
- All Photos sits above the saved folders. It shows every photo in each available saved folder and all its subfolders, ordered by folder as the expanded sidebar lists them; see [decision 0006](decisions/0006-all-photos.md). While it is selected, `Library` reads the folder tree one folder at a time with `FolderContents.read`, skipping folders already read, and the grid fills in folder by folder. Offline and missing locations are left out and named in the subtitle. The title is "All Photos". A thumbnail's help tag names the folder it is in.
- Under All Photos, the sidebar lists filter rows: Flagged, Rejected, Edited, then 5, 4, 3, 2 and 1 stars, each a `SidebarItem.filtered(PhotoFilter)`; see [decision 0029](decisions/0029-filter-rows-and-menu.md). Star rows match the exact rating and leave out rejected photos. Stars are drawn as star glyphs, with the rating as their VoiceOver label. The title is the row's name; a row with no matches shows "No Flagged Photos" and the like.
- A saved folder that is `missing` is dimmed and has a Locate… button that relinks it through `FileAccess`. One that is `offline` is dimmed without the button. Removing a folder asks first and says that photos and edits are not deleted.
- The window is in one of two modes, Browse or Edit, held in `BrowseState` together with the selected photo. Photos are identified by a `PhotoReference`, their folder and file name, so photos with the same name in different folders are told apart; `ListedPhoto` pairs a photo with its folder for the grid and the filmstrip. Both modes are dark in either system appearance; in Edit the canvas around the photo takes the color chosen in View › Canvas Color, a `CanvasColor` kept across launches, while the grid, sidebar and inspector keep the interface's 13% gray (see [decision 0036](decisions/0036-dark-interface-canvas-color.md)). The parts combine: each one set must match. While a filter is on, the button shows how many parts are set, from 1 to 3; its tooltip and VoiceOver label name them, such as "Flagged · 4+ Stars". A rating leaves rejected photos out unless the flag is Rejected. On a filter row, the row's criteria and the toolbar's are merged into one (`FilterCriteria.narrowed(by:)`), so the toolbar narrows the row further: Flagged with 4+ Stars shows flagged photos with four stars or more, and Rejected with 3 Stars shows rejected 3-star photos. Parts that can't both hold, such as the Flagged row with a Rejected flag, match no photo. The toolbar filter is kept when the sidebar selection changes; see [decision 0037](decisions/0037-filter-within-rows.md). The grid's top edge is the hard scroll edge style, so the title bar has the same fill and dividing line over the grid as over an empty view, and photos scrolled under it are blurred. The title is the folder name and the subtitle its photo count, or "12 of 120 photos" while filtered. A photo counts as edited when its `.proof` sidecar exists. A RAW followed by the JPEG or HEIC photos of the same name is a stack (`StackMark`): each is an ordinary tile with a stack mark in its top-left corner, and the RAW's shows the count. Stacks start collapsed to the RAW, with the photos it hides peeking out above it; the count badge opens them. `Library.shownPhotos` is `visiblePhotos` without the photos collapsed stacks hide, and is what the grid, the filmstrip, arrow keys and Select All use (decision 0049). When more photos are listed, such as when All Photos reads another folder, thumbnails already shown are kept. Click selects a photo and the arrow keys move the selection; Esc deselects every photo. ## Folder access

`FileAccess` in `ProofKit` is the only code that creates or resolves bookmarks. It hides how a folder was granted: on the Mac it stores a read-write security-scoped bookmark; on iOS the same `SystemBookmarks` stores a bookmark for a folder picked in the Files app, whose URL is security-scoped as on the Mac. Saved locations are kept as JSON in Application Support.

- Access to a folder covers every file and subfolder inside it. Adding a folder that is already saved, or sits inside a saved folder, returns the existing location. When saved folders are nested, a file belongs to the innermost one.
- Other code refers to a file as a `FileReference`: a location's identifier plus a path relative to it. A location keeps its identifier when it moves or is relinked, so references stay valid.
- When a location is resolved, a folder moved or renamed on the same volume is followed and a stale bookmark is replaced.
- A location that can't be resolved is kept. It is `offline` when its volume, such as a NAS share, isn't mounted; bookmarks are resolved without mounting so launch doesn't wait on the network. Otherwise it is `missing` and can be relinked to another folder.
- Proof writes only its own sidecars next to photos, never the photos themselves. Folders added or relinked now get read-write grants. Folders saved before that keep their read-only grant and `canWrite` is false; they stay browsable, and the first time Proof needs to write into one, `Library.ensureCanWrite(nextTo:)` opens the folder picker at that folder with Grant Access. `FileAccess.grantWriteAccess` accepts only that same folder (decision 0007). A location that is a single photo, saved by an early build, can't hold a sidecar, because the sandbox allows writing beside a file only through a grant to its folder. Proof asks for that folder in the same way, and the location becomes the folder, keeping its identifier (decision 0008).
- Removing a location forgets its grant. Photos, sidecars and edits on disk are not touched. Network shares are treated as slow: thumbnails come from the RAW file's embedded preview and are cached locally, and folders on network volumes are rescanned on demand instead of watched.
- Folders change without a relaunch. `FolderWatcher` in `ProofKit` watches the available saved folders on local disks with FSEvents, so local disks are never polled; a folder that changed is read again if it had been read. FSEvents doesn't report changes another computer makes on a network volume, so folders there are read again when Proof becomes the active app, and every read folder is read again with View › Reload Folders (⌘R). `ProofKit` builds for iOS too, where there is no FSEvents: there `FolderWatcher` reports nothing on its own (`FolderWatcher.reportsChanges` is false), so `Library` reads every read folder again when the app returns to the foreground, and the folder list's pull to refresh does the same (decision 0048). The system folder picker on iOS chooses one folder at a time, the one open when Open is tapped; `Library.chose(_:)` takes several URLs in case it allows more.
- When a drive or network share connects or disconnects, `Library` asks `FileAccess.recheck` for each location's status. A folder that becomes available is read and fills the sidebar, and All Photos reads it and stops naming it in the subtitle. One whose volume went away is `offline`, and what was read of it is forgotten so it is read fresh when it returns.

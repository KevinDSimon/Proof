# Architecture

Proof is split into a platform-neutral engine package, `ProofKit`, and thin app targets on top of it. The Mac app comes first; an iPad and iPhone app reuses `ProofKit` unchanged.

## Layers

| Layer | Owns | Never imports |
| --- | --- | --- |
| `ProofKit` | Edit recipe, render pipeline, sidecar and XMP reading, `.cube` parsing, thumbnails | AppKit, UIKit, SwiftUI |
| Mac app (`App/Proof.xcodeproj`) | Folders panel, filmstrip, inspector, canvas, export UI | — |
| iOS app (later) | The same panels for touch, Files-app folder picking | — |

The Mac app runs in the App Sandbox. Its project links `ProofKit` as a local Swift package, so a change to `ProofKit` is picked up by the next app build without a version bump. Until signing is set up in Phase 4, the app is signed to run locally only.

## Render pipeline

Every render starts from the original RAW file and applies the edit recipe in this order:

1. RAW decode in linear light with `CIRAWFilter`: exposure, white balance (temperature and tint), noise reduction, lens corrections
2. Tone: highlights and shadows, then contrast, whites, blacks and the tone curve baked together into one lookup per channel
3. Color: vibrance, saturation
4. LUT, applied with `CIColorCubeWithColorSpace` in display-referred Rec.709/sRGB and blended by strength
5. Layers (v1.2): each layer's mask and adjustments, blended in order with `CIBlendWithMask`
6. Quarter turns and flips, then straighten and crop, and the output transform to the display or export color space

`RAWRenderer` in `ProofKit` builds this graph from an `EditRecipe` in one function, `RAWRenderer.apply`, which the canvas and the thumbnails both use. Today it applies part of step 1 and steps 2, 3, 4 and 6: white balance, through `CIRAWFilter.neutralTemperature` and `neutralTint`, and exposure, in stops, through `CIRAWFilter.exposure`. Highlights and shadows follow the decode, in linear light, through a custom Metal kernel compiled when it is first used (see `docs/decisions/0009-highlights-shadows.md`); with both at 0 the stage is skipped. Contrast, whites, blacks and the tone curve follow as one lookup per channel, applied by a second kernel (see `docs/decisions/0010-tone-lookup.md` and `0011-tone-curve.md`); with the three sliders at 0 and every curve straight it is skipped too. Vibrance and saturation follow, still in linear light: vibrance through `CIVibrance`, which raises muted colors more than vivid ones and leaves grays alone, then saturation through `CIColorControls`, which changes all colors alike; each filter is skipped while its slider is at 0. Because they work in linear light, equal slider steps don't look equally large across the range. A perceptually even version would change how saved edits render, so it would come with a `processVersion` bump. The LUT stage converts the image from the linear working space to sRGB, looks each color up in the LUT with `CIColorCube`, blends the result with the image before the LUT by strength, still in sRGB, and converts back (see `docs/decisions/0013-applying-luts.md`). Strength runs from 0 to 1 and is clamped; at 0, or with no LUT loaded, the stage is skipped, so the photo renders exactly as with no look. The geometry stage turns and flips the photo, then turns it by the straighten angle around the crop rectangle's center and keeps only the rectangle, in whole pixels; the photo is clamped at its edges first, so a rectangle that touches them doesn't blend with nothing. The scale a render is decoded at fits the cropped photo, not the whole one, to the target size. The renderer reads the camera's white balance (As Shot) when it opens a photo, because it reuses one filter across renders and has to put those values back when an edit returns to As Shot. The other stages pass the image through until their controls are built. It is an actor, so decoding and GPU work run off the main thread. It opens a file once and renders it into a Metal texture scaled to fit a requested pixel size. Its `CIContext` caches intermediate results, so after the first render at a given size, a change to a later stage such as exposure reuses the decoded RAW data instead of decoding it again. Opening another photo clears the cache, so GPU memory holds the intermediates of one photo at a time. Cached and uncached renders of the same settings produce the same pixels. The Mac app's canvas is an `MTKView` that draws the latest texture scaled to the window; on resize it keeps drawing the old texture until a render at the new size finishes. The canvas runs one render at a time and never discards one in flight: while a slider is dragged faster than renders finish, each finished render is shown and the next starts from the slider's latest value.

`CubeLUT` in `ProofKit` reads 1D and 3D `.cube` files into a table of colors with its input domain, and reports malformed files with an error that names the line (see `docs/decisions/0012-cube-parser.md`). `PreparedLUT` lays a `CubeLUT` out as the 3D lattice over 0 to 1 that Core Image takes, once per LUT, and the renderer takes it next to the recipe. `LUTLibrary` finds the file `look.lut` names and prepares it (see the LUT library section below). 1D tables are sampled onto a 65-per-side lattice, tables with another domain onto 0 to 1, and tables larger than 128 per side, the most Core Image accepts, down to 128.

A render request always carries a target size. Interactive renders are always at the window's full size, including while a slider is dragged, so the photo never turns soft and a change to detail, such as Clarity, can be judged as it is made. With the decode cached, an exposure change renders at a full-screen size in 2–16 ms (median) on an M2 with a 60 MP DNG, inside one 30 fps frame. If a later stage is too slow for that, it is made faster rather than rendered at a reduced size. Only export renders at full sensor resolution.

## Files and data

| Data | Where it lives | Who writes it |
| --- | --- | --- |
| Original RAW | Its own folder | Never written |
| Ratings, flags and labels | XMP sidecar (`IMG_0001.xmp` or `IMG_0001.DNG.xmp`) or XMP embedded in the DNG | Other apps; Proof reads only |
| Edit recipe | `IMG_0001.DNG.proof` next to the original, JSON | Proof |
| Thumbnails, folder index | Application Support | Proof; disposable |

See [edit-format.md](edit-format.md) for the recipe format.

### Edits

`Sidecar` in `ProofKit` reads and writes a photo's `.proof` file with `NSFileCoordinator`. It keeps the JSON it read, so saving keeps fields this version doesn't recognize. Saving a neutral recipe deletes the file instead, unless it has unrecognized fields; a photo with no sidecar and a neutral edit gets no file (decision 0007). Revert to Original deletes the file whatever it holds, as one undo step; undoing it saves the edit as a new file.

When a photo is first opened in Edit, `Library` reads its sidecar into a `PhotoEdit`, which holds the recipe the controls show and an `EditHistory`. Each undo step is a whole recipe. A slider drag becomes one step when it ends; a change made without a drag, such as a double-click reset, becomes one once the controls have been idle for 0.4 seconds. Each step is saved as soon as it is made. Each photo keeps its edit and undo history in memory until Proof quits, so returning to a photo still allows undo. Edit › Undo and Redo (⌘Z, ⇧⌘Z) apply to the photo open in Edit.

Before writing, `Library` checks `ensureCanWrite(nextTo:)`. If the folder hasn't been granted again for writing, the folder picker opens once per folder per session, and the change stays in memory with a note in the inspector, which offers Grant Access…. Edits waiting on that folder are saved once it is granted. A photo saved on its own by an early build is granted through its folder the same way (decision 0008). A sidecar that can't be read is never written over. Sidecars are read and written on the main thread; they are small, but a slow network volume can delay a save.

### LUT library

`LUTLibrary` in `ProofKit` keeps the person's LUTs as `.cube` files in `Application Support/Proof/LUTs`, inside Proof's own container, and `look.lut` names one by its file name (decision 0014). Proof ships with none. Importing, by the Look section's Import… button or by dropping files on it, parses each file first; a file the parser refuses isn't copied, and the parser's message is shown. A file whose name is taken by one with other contents is numbered, as in "Portra 2.cube", so a LUT an edit names never changes. The library is an actor: each LUT is read and prepared once, off the main thread, and kept prepared up to 512 MB, letting the least recently used go first. The canvas, edited thumbnails and Auto straighten all ask it for the LUT a recipe names, so switching between looks that have been previewed renders at the speed of any other change. A LUT that isn't in the library is skipped, and the Look section says so.

The Look section shows a preview of the photo in Edit through each LUT. The photo is rendered once, 256 pixels on the long edge, with its edit but no look, and each LUT is applied to that small image, so the RAW file is decoded once for all previews. The previews are kept until the photo or the rest of its edit changes, and are made again a quarter second after a change rests.

### Thumbnails

`ThumbnailCache` in `ProofKit` makes and stores thumbnails, 512 pixels on the long edge, as JPEG files in `Application Support/Proof/Thumbnails`. A thumbnail comes from the JPEG preview that the camera or DNG converter embedded in the RAW file, so the RAW data isn't decoded. Only a file without an embedded preview is decoded in full.

Each photo has a folder in the cache named from a hash of its path, and the thumbnail inside is named from a hash of the file's size and modification date. A file whose size or date changed misses the cache, and storing its new thumbnail removes the old one. The size and date are read from the file system on every lookup, because a `URL` keeps resource values it has already read. Thumbnails of photos that were deleted or moved stay in the cache until it is cleared; the cache can be deleted at any time.

An edited photo's thumbnail is rendered from the RAW file with its edit instead, by a `RAWRenderer` of its own, so it matches the photo in Edit and never delays the canvas. Its cache file is also named from the edit, so a changed edit misses the cache. When a folder is listed, the sidecars of photos marked as edited are read to find their edits; on a NAS that is one extra read per edited photo, and rendering an edited thumbnail the first time is slower than reading an embedded preview. After each change in Edit, `Library` renders the photo's thumbnail again and the grid and the filmstrip show it in place of the one they loaded.

For a folder, cached thumbnails arrive first, then the missing ones are made four at a time so a NAS isn't asked for the whole folder at once. A file that can't be read arrives without an image and doesn't stop the rest.

## Window layout

The Mac app has one window. Panels sit beside the photo and never cover it; see [decision 0004](decisions/0004-window-layout.md).

- The sidebar is a `NavigationSplitView` sidebar listing the saved folders. Each one expands into its subfolders exactly as they are on disk; Proof doesn't group or reorganize them. Each row shows how many RAW photos sit directly in that folder. A folder is read with `FolderContents.read` off the main thread when its row first appears, so a tree on a NAS costs one directory listing per visible folder.
- All Photos sits above the saved folders. It shows every RAW photo in each available saved folder and all its subfolders, ordered by folder as the expanded sidebar lists them; see [decision 0006](decisions/0006-all-photos.md). While it is selected, `Library` reads the folder tree one folder at a time with `FolderContents.read`, skipping folders already read, and the grid fills in folder by folder. Offline and missing locations are left out and named in the subtitle. The title is "All Photos". A thumbnail's help tag names the folder it is in.
- A saved folder that is `missing` is dimmed and has a Locate… button that relinks it through `FileAccess`. One that is `offline` is dimmed without the button. Removing a folder asks first and says that photos and edits are not deleted.
- The window is in one of two modes, Browse or Edit, held in `BrowseState` together with the selected photo. Photos are identified by a `PhotoReference`, their folder and file name, so photos with the same name in different folders are told apart; `ListedPhoto` pairs a photo with its folder for the grid and the filmstrip. Both modes follow the system's light or dark appearance. Browse shows the sidebar, a thumbnail grid of the selected folder and the All, 5 Stars and Edited filter (`PhotoFilter`). The title is the folder name and the subtitle its photo count. A photo counts as edited when its `.proof` sidecar exists. 5 Stars shows photos rated five stars in XMP that aren't rejected. `FolderContents.read` reads XMP sidecars while listing the folder; for photos without one, `Library` reads the XMP embedded in each photo of the selected folder, or of All Photos, in the background, so those photos join the filter as they are read. `PhotoMetadata` holds the rating, the flag (unflagged, flagged or rejected) and the label; see [decision 0005](decisions/0005-reading-xmp.md) for how each app's XMP is read.
- The grid shows each thumbnail as soon as `ThumbnailCache` delivers it, so a folder on a NAS fills in while it is read. Thumbnails are loaded for every photo in the folder, so changing the filter doesn't read it again. When more photos are listed, such as when All Photos reads another folder, thumbnails already shown are kept. Click selects a photo and the arrow keys move the selection; double-click or Return enters Edit. A photo the filter hides is deselected.
- Edit hides the sidebar, restoring it on return. The title is the photo name and the subtitle the folder and the photo's position among the photos that pass the filter ("3 of 120"). The toolbar has a back button at the leading end, and at the trailing end the stars and the flags, as two groups, then the crop button and the inspector button, each a group of its own; the title stands on its own beside the back button. The back button and Esc return to Browse with the same photo selected. While cropping, Cancel and Done take the crop button's place. The adjustments sit in an `.inspector` panel beside the photo and show the photo's saved edit. White Balance has a preset menu (As Shot, Daylight, Cloudy, Shade, Tungsten, Fluorescent, Flash, and Custom once a slider has moved), Temperature in Kelvin and Tint; Light has Exposure, Highlights and Shadows. Each value can be typed, and Up and Down arrows step it, by more with Shift and by less with Option. Double-clicking an adjustment's name or its slider resets it, and each section header has a Reset button. Each slider's track shows what it does to the photo, as in Lightroom: Temperature runs blue to yellow and Tint green to magenta, each color fading toward a light middle rather than blending through gray, Exposure runs black to white, Highlights gray to white and Shadows black to gray. These tracks and the histogram are the only color in the interface. The Temperature slider is spaced evenly in mireds (a million divided by the Kelvin), so the common range of 2000–10000 K takes most of its length.
- Crop (C, or the toolbar's crop button) opens the crop tool. The inspector shows the crop controls in place of the adjustments, and the canvas shows the whole photo, turned and flipped, with the crop rectangle drawn over it and the photo outside it faded toward the canvas. The rectangle's corners and edges are dragged to resize it and its inside to move it; a rule-of-thirds grid shows while dragging, and a finer grid while straightening. The rectangle always lies on the photo: a drag stops at its edges, and straightening shrinks the rectangle around its center just enough. The tool keeps the rectangle from before straightening, so it grows back as the angle returns to zero. The canvas tilts the photo as it draws it rather than rendering again, so straightening follows the slider without waiting. The Crop section has the aspect ratio menu (Freeform, Original, 1:1, 4:5, 5:7, 3:2, 16:9, Custom, where Custom takes a typed ratio), Swap (X) for landscape or portrait, Straighten from −45° to 45°, and Level. Level's ruler button turns the next drag on the photo into a line, and the photo straightens so that line is level, or upright when it is drawn closer to vertical. Its Auto button renders the photo, turned and flipped but not straightened, at about 1024 pixels and asks Vision (`DetectHorizonRequest`) for the horizon; when Vision finds none, the angle stays as it was and a note under Level reads No horizon found for two seconds. Dragging just outside a corner of the rectangle also straightens: the photo turns with the pointer around the rectangle's center. Both set the same angle as the slider, within its range; the math is in `ProofKit` (`Horizon`). Rotate and Flip has a quarter turn each way and a flip each way. The ratio starts at Original for a photo without a crop. A preset takes the current rectangle's orientation. Each section header has a Reset button. Done (Return) keeps the crop, and Cancel (Esc) returns to the edit from when the tool opened, as one undo step. Leaving the photo any other way keeps the crop. The geometry is computed in `ProofKit` (`Crop` and `CropFrame`), so it is tested without the app.
- A red, green and blue histogram is the inspector's first section, Histogram, on the same card as the other sections. Each channel is a see-through fill with a solid outline, so every channel's shape stays readable where they overlap. In the dark appearance the fills add like light, so where all three overlap they show as gray; in the light appearance they are layered, because adding them on a light card would wash them out. The section's footer shows the photo's ISO, focal length, aperture and shutter speed, read from its EXIF when it opens in Edit (`CaptureSettings` in `ProofKit`); any the photo doesn't record are left out. It counts the render the canvas shows, at screen size, with `CIAreaHistogram` in Display P3, the encoded values on screen rather than linear light. Its height is scaled to the tallest bin other than pure black and pure white, so clipped shadows or highlights show as a spike at the edge without flattening the rest. The canvas measures each finished render beside its render loop, not in it, so a slider drag never waits for the histogram; like renders, one measurement runs at a time and the next takes the latest photo shown. A measurement of a 2560×1600 render takes about 6 ms (median) on an M2. VoiceOver reads the share of clipped shadows and highlights.
- A filmstrip runs under the photo in Edit, one row of thumbnails of the photos that pass the filter, from the same `ThumbnailCache`. The current photo has a ring and is scrolled to the middle. Click or the left and right arrow keys switch photos without leaving Edit; the arrows stop at the first and last photo.
- The canvas in Edit is white in the light appearance and 13% gray in the dark, so the whole window changes with the system. It runs under the toolbar glass and stops at the inspector, which has the same plain color instead of its usual material, so the photo and its panel read as one surface. The sidebar and the Browse area use the same color, so the whole window is one surface in either mode. The toolbar uses the system's default background and scroll edge effect: content that scrolls under it, such as the grid's thumbnails, is blurred behind the toolbar material, so the title and subtitle stay readable. Proof doesn't hide or restyle the toolbar background. The photo is centered with a margin and stays inside the safe area.
- Proof's own interface uses only black, white and gray, so no color competes with the photo. The app's accent color is black in the light appearance and 40% gray in the dark; it colors the focused sidebar selection, the filter and the slider. White would make the selected row's text unreadable, because macOS keeps that text white. A selected thumbnail in the grid or the filmstrip has a ring a few points outside the photo, black in light and white in dark, and no fill. Folder symbols in the sidebar are gray. macOS uses an app's accent color only when the system accent is Multicolor; with another system accent, that color shows instead.
- Thumbnails in the grid and the filmstrip show what other apps recorded in XMP: a flag in the photo's top-right corner if it is flagged, and the rating as a star and a number in its bottom-left, in white on a dark backing. Unflagged and unrated photos show nothing. A rejected photo has no flag badge and is dimmed to 35% opacity, as in Lightroom. VoiceOver reads the rating and flag after the photo's name. The grid shows each photo's file name centered under it; photos sit on the bottom of their square so the name is directly under every photo.
- In Edit, the toolbar has two groups of buttons: five stars, and Flagged, Unflagged and Rejected. Clicking a star sets the rating and clicking the current one clears it; the current flag is shown selected. The flag icons follow Lightroom: a filled flag, an outlined flag, and a filled flag with an X cut out of it (SF Symbols has no such symbol). The Photo menu has the same choices with Lightroom's keys: 0 to 5 for stars, P, U and X for the flag, in Browse and Edit.
- Changed ratings and flags are kept only in memory. Proof doesn't write XMP yet, so a change lasts until Proof quits, and other apps don't see it. When a folder is read again, a changed rating stays unless the photo's XMP sidecar has one; XMP read from inside a photo is kept the same way. A photo whose rating or flag changed stays visible until the filter or folder changes, even if the filter no longer matches it. XMP read in the background never replaces a rating already changed.
- Every toolbar action is also in the menu bar: Add Folder in File; Undo and Redo of edits in Edit; the filter (All, 5-Star Photos and Edited Photos, ⌘1–⌘3), Reload Folders (⌘R), Show Sidebar and Show Inspector (⌃⌘I) in View; Edit (Return), Back to Folder (Esc), Crop (C), Rotate Left (⌘[), Rotate Right (⌘]), Flip Horizontal, Flip Vertical, Rating (0–5) and Flag (P, U, X) in Photo. While cropping, Photo has Done Cropping (Return), Cancel Cropping (Esc) and Swap Crop Orientation (X) in place of Crop, and X no longer rejects the photo.
- The sidebar selection, All Photos or a folder's `FileReference`, is remembered between launches. A selection saved before All Photos existed is still read. The selected photo is not remembered.

## Folder access

`FileAccess` in `ProofKit` is the only code that creates or resolves bookmarks. It hides how a folder was granted: on the Mac it stores a read-write security-scoped bookmark; on iOS, a `BookmarkSystem` for folders picked in the Files app can take its place. Saved locations are kept as JSON in Application Support.

- Access to a folder covers every file and subfolder inside it. Adding a folder that is already saved, or sits inside a saved folder, returns the existing location. When saved folders are nested, a file belongs to the innermost one.
- Other code refers to a file as a `FileReference`: a location's identifier plus a path relative to it. A location keeps its identifier when it moves or is relinked, so references stay valid.
- When a location is resolved, a folder moved or renamed on the same volume is followed and a stale bookmark is replaced.
- A location that can't be resolved is kept. It is `offline` when its volume, such as a NAS share, isn't mounted; bookmarks are resolved without mounting so launch doesn't wait on the network. Otherwise it is `missing` and can be relinked to another folder.
- Proof writes only its own sidecars next to photos, never the photos themselves. Folders added or relinked now get read-write grants. Folders saved before that keep their read-only grant and `canWrite` is false; they stay browsable, and the first time Proof needs to write into one, `Library.ensureCanWrite(nextTo:)` opens the folder picker at that folder with Grant Access. `FileAccess.grantWriteAccess` accepts only that same folder (decision 0007). A location that is a single photo, saved by an early build, can't hold a sidecar, because the sandbox allows writing beside a file only through a grant to its folder. Proof asks for that folder in the same way, and the location becomes the folder, keeping its identifier (decision 0008).
- Removing a location forgets its grant. Photos, sidecars and edits on disk are not touched. Network shares are treated as slow: thumbnails come from the RAW file's embedded preview and are cached locally, and folders on network volumes are rescanned on demand instead of watched.
- Folders change without a relaunch. `FolderWatcher` in `ProofKit` watches the available saved folders on local disks with FSEvents, so local disks are never polled; a folder that changed is read again if it had been read. FSEvents doesn't report changes another computer makes on a network volume, so folders there are read again when Proof becomes the active app, and every read folder is read again with View › Reload Folders (⌘R).
- When a drive or network share connects or disconnects, `Library` asks `FileAccess.recheck` for each location's status. A folder that becomes available is read and fills the sidebar, and All Photos reads it and stops naming it in the subtitle. One whose volume went away is `offline`, and what was read of it is forgotten so it is read fresh when it returns.

# Architecture

Proof is split into a platform-neutral engine package, `ProofKit`, and thin app targets on top of it. The Mac app comes first; an iPad and iPhone app reuses `ProofKit` unchanged.

## Layers

| Layer | Owns | Never imports |
| --- | --- | --- |
| `ProofKit` | Edit recipe, render pipeline, sidecars, XMP reading, rating and description writes, `.cube` parsing, thumbnails | AppKit, UIKit, SwiftUI |
| Mac app (`App/Proof.xcodeproj`) | Folders panel, filmstrip, inspector, canvas, export UI | — |
| iOS app (later) | The same panels for touch, Files-app folder picking | — |

The Mac app runs in the App Sandbox. Its project links `ProofKit` as a local Swift package, so a change to `ProofKit` is picked up by the next app build without a version bump. Until signing is set up in Phase 8, the app is signed to run locally only.

## Render pipeline

Every render starts from the original RAW file and applies the edit recipe in this order:

1. RAW decode in linear light with `CIRAWFilter`: exposure, white balance (temperature and tint), sharpening and noise reduction (decision 0016), lens corrections, then perspective (decision 0025), then halation and bloom (decision 0028)
2. Tone: highlights and shadows, then texture and clarity, then dehaze, then contrast, whites, blacks and the tone curve baked together into one lookup per channel
3. Color: vibrance, saturation, selective color, black and white
4. LUT, applied with `CIColorCubeWithColorSpace` in display-referred Rec.709/sRGB and blended by strength
5. Layers (v1.2): each layer's mask and adjustments, blended in order with `CIBlendWithMask`
6. Quarter turns and flips, then straighten and crop
7. Vignette, then grain, on the cropped frame, and the output transform to the display or export color space

`RAWRenderer` in `ProofKit` builds this graph from an `EditRecipe` in one function, `RAWRenderer.apply`, which the canvas and the thumbnails both use. Today it applies step 1 and steps 2, 3, 4, 6 and 7: white balance, through `CIRAWFilter.neutralTemperature` and `neutralTint`, and exposure, in stops, through `CIRAWFilter.exposure`. Highlights and shadows follow the decode, in linear light, through a custom Metal kernel compiled when it is first used (see `docs/decisions/0009-highlights-shadows.md`); with both at 0 the stage is skipped. Texture and clarity follow, also in linear light, through a third kernel that compares each pixel's brightness with a small blur (texture) and with an edge-aware map of its area (clarity) and scales the difference (see `docs/decisions/0017-texture-clarity.md`); with both at 0 it is skipped. Dehaze follows, through kernels that measure haze on a small map of the photo with the dark-channel prior, estimate the haze's color, and remove or add haze following the photo's edges (see `docs/decisions/0020-dehaze.md`); at 0 it is skipped. Contrast, whites, blacks and the tone curve follow as one lookup per channel, applied by a second kernel (see `docs/decisions/0010-tone-lookup.md` and `0011-tone-curve.md`); with the three sliders at 0 and every curve straight it is skipped too. Vibrance and saturation follow, still in linear light: vibrance through `CIVibrance`, which raises muted colors more than vivid ones and leaves grays alone, then saturation through `CIColorControls`, which changes all colors alike; each filter is skipped while its slider is at 0. Because they work in linear light, equal slider steps don't look equally large across the range. A perceptually even version would change how saved edits render, so it would come with a `processVersion` bump. Selective color follows, through one more kernel that finds each pixel's hue, weighs it between the two nearest of eight color ranges, and turns its hue, scales its saturation and changes its brightness by those ranges' values, fading out toward gray (see `docs/decisions/0026-selective-color.md`); with every range at 0 it is skipped. The black-and-white mix follows, through `CIColorMatrix`, which sets every channel to the same weighted blend of red, green and blue (see `docs/decisions/0027-black-and-white.md`); while the treatment is Color it is skipped. The histogram measured from each canvas render also counts the photo's hues, for the Selective Color card's graph; while the photo is black and white, the hues are counted in a small copy rendered without the mix, so the graph keeps showing the colors Selective Color adjusts. The LUT stage converts the image from the linear working space to sRGB, looks each color up in the LUT with `CIColorCube`, blends the result with the image before the LUT by strength, still in sRGB, and converts back (see `docs/decisions/0013-applying-luts.md`). Strength runs from 0 to 1 and is clamped; at 0, or with no LUT loaded, the stage is skipped, so the photo renders exactly as with no look. The geometry stage turns and flips the photo, then turns it by the straighten angle around the crop rectangle's center and keeps only the rectangle, in whole pixels; the photo is clamped at its edges first, so a rectangle that touches them doesn't blend with nothing. The vignette follows, through one more kernel that darkens or lightens each pixel by its distance from the cropped frame's center, so it follows any crop and a zoomed region matches the whole frame (see `docs/decisions/0021-vignette.md`); with Amount at 0 it is skipped. Grain follows, through one more kernel that adds value noise sized relative to the cropped frame; below full resolution each pixel shows the average of the grains it covers, so the canvas shows the grain an export shrunk to the same size would have (decision 0028). With Amount at 0 it is skipped. The scale a render is decoded at fits the cropped photo, not the whole one, to the target size. Sharpening and noise reduction are set on the same filter; `null` values keep the camera's defaults, and the decoder sharpens only above half size. The lens profile is set there too, through `CIRAWFilter.isLensCorrectionEnabled`, and only for files where `isLensCorrectionSupported` is true; other files, such as Leica M DNGs, which carry no correction data, are left alone. An edit without its own setting keeps the decoder's default. Chromatic aberration is corrected right after the decode, by a kernel that reads red and blue at the scales the edit stores, about the photo's center; Proof measures those scales from the photo when Remove Chromatic Aberration is turned on (see `docs/decisions/0023-chromatic-aberration.md`). Manual lens vignetting and distortion follow, for lenses without a profile, still about the uncropped photo's center: one kernel scales each pixel like exposure by its distance from the center, and another reads each pixel from a radius scaled by a one-term radial model, with the photo enlarged just enough to fill the frame (see `docs/decisions/0024-manual-lens-corrections.md`). Each is skipped at 0. Perspective follows, through `CIPerspectiveTransform`, still on the whole photo as the camera oriented it, so it comes before the crop's turns and stays with the photo when it is turned: the four corners go where a homography for the Transform sliders puts them, enlarged to fill the frame while Constrain Crop is on (see `docs/decisions/0025-perspective.md`). It is skipped while the sliders are neutral. Halation and bloom follow, still on the whole photo, so light from outside the crop spreads into it: one kernel keeps the highlights of a 2048-pixel copy of the photo, counting lights near the clip point as up to 4 stops brighter unless their surroundings are bright too; the result is shrunk to a 1024-pixel map, which is cached, and blurred by a share of the photo's long edge, and another kernel adds what spills past each pixel's own highlights, mostly in red for halation and in every color for bloom (see `docs/decisions/0028-effects.md`). With both Amounts at 0 the stage is skipped. Upright finds straight segments in a 1024-pixel render of the uncorrected photo (`LineDetector`) and solves for the sliders (`Upright`), both in `ProofKit`. The renderer reads the camera's white balance (As Shot), its default sharpening and noise reduction, and whether it has a lens profile and applies it by default when it opens a photo, because it reuses one filter across renders and has to put those values back when an edit returns to them. Auto white balance and Auto Tone measure a render of about 256 pixels with the same function and write ordinary slider values to the edit; the white balance is found by rendering a few candidates (see `docs/decisions/0018-auto-adjust.md`). The white balance eyedropper uses the same search but measures only a small patch around the click, rendered on its own (see `docs/decisions/0019-white-balance-eyedropper.md`). The other stages pass the image through until their controls are built. It is an actor, so decoding and GPU work run off the main thread. It opens a file once and renders it into a Metal texture scaled to fit a requested pixel size. Its `CIContext` caches intermediate results, so after the first render at a given size, a change to a later stage such as exposure reuses the decoded RAW data instead of decoding it again. Opening another photo clears the cache, so GPU memory holds the intermediates of one photo at a time. Cached and uncached renders of the same settings produce the same pixels. The Mac app's canvas is an `MTKView` that draws the latest texture scaled to the window; on resize it keeps drawing the old texture until a render at the new size finishes. The canvas runs one render at a time and never discards one in flight: while a slider is dragged faster than renders finish, each finished render is shown and the next starts from the slider's latest value. A photo opened in Edit, or stepped to in the filmstrip, shows its cached thumbnail at once while its first render runs: the thumbnail of its current edit, which the grid and the filmstrip show too, so it already has the edit's crop and colors. It is looked up with `ThumbnailCache.cachedThumbnail(for:edit:)`, which never renders, and drawn by `RAWRenderer.placeholder` into the frame of the cropped photo's full size. That size is read from the file's header with ImageIO, which on a NAS takes about 7 ms where opening the file with `CIRAWFilter` takes 110–340 ms; for the Leica DNGs checked, both give the same size, and a test compares it with a render's on the sample photo. That is the frame the render fills, so the render replaces the thumbnail without moving the photo, even when the thumbnail's own shape differs slightly. A photo without a cached thumbnail shows a small progress indicator where it will appear until its render is ready. The canvas draws, and makes these placeholders, with a Core Image context and command queue of its own, so a new photo's thumbnail never waits behind the decode of the photo before it; with the shared context, the previous photo stayed on screen under the new photo's name until its decode finished. A render can't be stopped once it starts, so a render for a photo that is no longer shown is dropped before each step that can be skipped: before the file is opened and before the photo is rendered. While stepping quickly, at most the one render already in flight finishes, and the next one starts from the photo shown then. Errors from a photo no longer shown aren't reported.

`CubeLUT` in `ProofKit` reads 1D and 3D `.cube` files into a table of colors with its input domain, and reports malformed files with an error that names the line (see `docs/decisions/0012-cube-parser.md`). `PreparedLUT` lays a `CubeLUT` out as the 3D lattice over 0 to 1 that Core Image takes, once per LUT, and the renderer takes it next to the recipe. `LUTLibrary` finds the file `look.lut` names and prepares it (see the LUT library section below). 1D tables are sampled onto a 65-per-side lattice, tables with another domain onto 0 to 1, and tables larger than 128 per side, the most Core Image accepts, down to 128.

A render request always carries a target size. Interactive renders are always at the window's full size, including while a slider is dragged, so the photo never turns soft and a change to detail, such as Clarity, can be judged as it is made. With the decode cached, an exposure change renders at a full-screen size in 2–16 ms (median) on an M2 with a 60 MP DNG, inside one 30 fps frame. If a later stage is too slow for that, it is made faster rather than rendered at a reduced size. Only export renders at full sensor resolution.

Zoom renders only what the view shows. `Viewport` in `ProofKit` holds the zoom, as screen pixels per photo pixel or Fit, and the photo point at the view's center; it gives the photo's frame in the view, with its origin in whole pixels so that 100% puts one photo pixel on one screen pixel, and the part of the photo that is visible. While the view shows the photo larger than the screen-size render, the canvas asks `RAWRenderer.render(region:scale:)` for the visible part, plus an eighth of the view past each edge, at the view's scale up to full resolution. The region is cropped from the same graph after the geometry stage, so Core Image computes only that part, and its pixels are the same as that part of a full-resolution render (a test checks this on the sample photo). Past 100% the region is rendered at full resolution and enlarged on screen, nearest pixel first, so pixels stay crisp. The canvas draws the screen-size render, enlarged, under the region, so a pan moves at once and the edges it uncovers show soft until the next region is ready. While zoomed, the region renders before the screen-size photo, which then catches up for the histogram and for those edges. On an M2 with the 60 MP sample in a 2560×1600 view at 100%, a region of the view alone renders in about 49 ms (median), a region with the margin in about 81 ms, and an exposure change on a region in about 4 ms.

## Files and data

| Data | Where it lives | Who writes it |
| --- | --- | --- |
| Original RAW | Its own folder | Never written |
| Ratings, flags and labels | XMP sidecar (`IMG_0001.xmp` or `IMG_0001.DNG.xmp`) or XMP embedded in the DNG | Other apps; Proof writes ratings and flags to the sidecar only |
| Title, caption, keywords, creator, copyright, location | The same XMP sidecar or embedded XMP, then IPTC and the camera's artist and copyright | Other apps; Proof writes them to the sidecar only |
| Edit recipe | `IMG_0001.DNG.proof` next to the original, JSON | Proof |
| Thumbnails, folder index | Application Support | Proof; disposable |

See [edit-format.md](edit-format.md) for the recipe format.

### Edits

`Sidecar` in `ProofKit` reads and writes a photo's `.proof` file with `NSFileCoordinator`. It keeps the JSON it read, so saving keeps fields this version doesn't recognize. Saving a neutral recipe deletes the file instead, unless it has unrecognized fields; a photo with no sidecar and a neutral edit gets no file (decision 0007). Revert to Original deletes the file whatever it holds, as one undo step; undoing it saves the edit as a new file.

When a photo is first opened in Edit, `Library` reads its sidecar into a `PhotoEdit`, which holds the recipe the controls show and an `EditHistory`. Each undo step is a whole recipe. A slider drag becomes one step when it ends; a change made without a drag, such as a double-click reset, becomes one once the controls have been idle for 0.4 seconds. Each step is saved as soon as it is made. Each photo keeps its edit and undo history in memory until Proof quits, so returning to a photo still allows undo. Edit › Undo and Redo (⌘Z, ⇧⌘Z) apply to the photo open in Edit.

Edit › Copy (⌘C) opens a sheet, as Lightroom's Copy Settings does, with checkboxes in three columns grouped by inspector card: each card has a checkbox, which shows a dash while only some of its items are ticked, over one for each slider or section on it, such as Exposure, Treatment, Noise Reduction, Remove Chromatic Aberration or Grain. Cards with one control, such as Curve and Look, are a single checkbox, and Crop sits beside Transform. All but Transform and Crop start ticked, since they fit the photo they came from and suit others only when nothing moved, as on a tripod; the ticks are remembered. Copy works in Browse too, from the selected photo, or from the one with the stronger outline when several are selected. Edit › Paste (⌘V) replaces those items of every selected photo with the copied values, in Browse or Edit, as one undo step in each photo's own history that is saved like any other; in Edit it turns on the switches of the cards it changed. A photo that hasn't been opened in Edit has its sidecar read first. Transform comes across whole, its guides and Upright mode included. Crop copies the rectangle with the turns, flips, straighten angle and ratio, because the rectangle lies in the photo as turned and flipped. What is copied stays in memory until Proof quits; nothing goes to the system pasteboard. While a field is being typed in, ⌘C and ⌘V copy and paste its text instead; Copy Settings… and Paste Settings in the same menu always act on settings. `SettingsItem` and `EditRecipe.pasting` in `ProofKit` decide what each item covers.

Before writing, `Library` checks `ensureCanWrite(nextTo:)`. If the folder hasn't been granted again for writing, the folder picker opens once per folder per session, and the change stays in memory with a note in the inspector, which offers Grant Access…. Edits waiting on that folder are saved once it is granted. A photo saved on its own by an early build is granted through its folder the same way (decision 0008). A sidecar that can't be read is never written over. Sidecars are read and written on the main thread; they are small, but a slow network volume can delay a save.

### LUT library

`LUTLibrary` in `ProofKit` keeps the person's LUTs as `.cube` files in `Application Support/Proof/LUTs`, inside Proof's own container, and `look.lut` names one by its path there, such as `Portra/400.cube` (decision 0014). Proof ships with none. Add Looks… in the Looks section's folder pop-up, or a drop on its list, imports `.cube` files and folders; a folder keeps its name and subfolders, and other files in it are left out. Each file is parsed first; one the parser refuses isn't copied, and the parser's message is shown. A file whose name is taken in its folder by one with other contents is numbered, as in "Portra 2.cube", so a LUT an edit names never changes. The library is an actor: each LUT is read and prepared once, off the main thread, and kept prepared up to 512 MB, letting the least recently used go first. The canvas, edited thumbnails and Auto straighten all ask it for the LUT a recipe names, so switching between looks that have been previewed renders at the speed of any other change. A LUT that isn't in the library is skipped, and the Looks section says so.

The Looks section shows one folder of the library at a time, chosen from a full-width pop-up button titled with the chosen look, whose folders with subfolders open as submenus, and shows that folder's LUTs three across as previews of the photo in Edit through each. The photo is rendered once, 160 pixels on the long edge, with its edit but no look, and each LUT is applied to that small image, so the RAW file is decoded once for all previews. The previews are kept until the photo or the rest of its edit changes, and are made again a quarter second after a change rests. With the grid focused, the arrow keys move between tiles and choose as they go; Photo › Next Look and Previous Look step through the shown folder from anywhere in Edit. Proof reads the library's folder again whenever it becomes active, so changes made in the Finder through Reveal in Finder appear.

### Export

File › Export… (⇧⌘E) and the right-click menu open `ExportSheet` for the selected photos: format, size, color space and Remove Location, remembered between exports as `ExportSettings`. `ExportQueue` in the app exports one photo at a time in the background with a `RAWRenderer` of its own. `RAWRenderer.export` decodes the file at the scale that fits the size asked for and applies the same graph as the canvas, then makes the size exact and renders into a bitmap without alpha, 16 bits per channel for TIFF. `PhotoExport` writes it with ImageIO, with the original's Exif, TIFF and GPS properties and the rating and description as IPTC and XMP, next to any file of the same name rather than over it. Each photo is exported with its edit as it was when Export was clicked. The toolbar shows progress, Stop Export and a summary. See [decision 0031](decisions/0031-export.md). Saved destinations, a folder and settings under a name, are kept by `ExportDestinations` in `ProofKit`, with their folder grants made and resolved by `FileAccess`. The sheet's Export To picker and File › Export To export to one without an open panel. See [decision 0032](decisions/0032-export-destinations.md).

### Thumbnails

`ThumbnailCache` in `ProofKit` makes and stores thumbnails, 512 pixels on the long edge, as JPEG files in `Application Support/Proof/Thumbnails`. A thumbnail comes from the JPEG preview that the camera or DNG converter embedded in the RAW file, so the RAW data isn't decoded. Only a file without an embedded preview is decoded in full.

Each photo has a folder in the cache named from a hash of its path, and the thumbnail inside is named from a hash of the file's size and modification date. A file whose size or date changed misses the cache, and storing its new thumbnail removes the old one. The size and date are read from the file system on every lookup, because a `URL` keeps resource values it has already read. Thumbnails of photos that were deleted or moved stay in the cache until it is cleared; the cache can be deleted at any time.

An edited photo's thumbnail is rendered from the RAW file with its edit instead, by a `RAWRenderer` of its own, so it matches the photo in Edit and never delays the canvas. Its cache file is also named from the edit, and from the version of the LUT the edit's look names, so a changed edit or LUT misses the cache; a look whose LUT is missing is left out, as on the canvas. When a folder is listed, the sidecars of photos marked as edited are read to find their edits; on a NAS that is one extra read per edited photo, and rendering an edited thumbnail the first time is slower than reading an embedded preview. After each change in Edit, `Library` renders the photo's thumbnail again and the grid and the filmstrip show it in place of the one they loaded. The canvas shows the same cached thumbnail while a photo's first render runs (see the render pipeline above).

For a folder, cached thumbnails arrive first, then the missing ones are made four at a time so a NAS isn't asked for the whole folder at once. A file that can't be read arrives without an image and doesn't stop the rest.

## Window layout

The Mac app has one window. Panels sit beside the photo and never cover it; see [decision 0004](decisions/0004-window-layout.md).

- The sidebar is a `NavigationSplitView` sidebar listing the saved folders. Each one expands into its subfolders exactly as they are on disk; Proof doesn't group or reorganize them. Each row shows how many RAW photos sit directly in that folder. A folder is read with `FolderContents.read` off the main thread when its row first appears, so a tree on a NAS costs one directory listing per visible folder.
- All Photos sits above the saved folders. It shows every RAW photo in each available saved folder and all its subfolders, ordered by folder as the expanded sidebar lists them; see [decision 0006](decisions/0006-all-photos.md). While it is selected, `Library` reads the folder tree one folder at a time with `FolderContents.read`, skipping folders already read, and the grid fills in folder by folder. Offline and missing locations are left out and named in the subtitle. The title is "All Photos". A thumbnail's help tag names the folder it is in.
- Under All Photos, the sidebar lists filter rows: Flagged, Rejected, Edited, then 5, 4, 3, 2 and 1 stars, each a `SidebarItem.filtered(PhotoFilter)`; see [decision 0029](decisions/0029-filter-rows-and-menu.md). Each shows the photos across folders that match, read the same way as All Photos, and its count of matching photos read so far, zero included. Star rows match the exact rating and leave out rejected photos. Stars are drawn as star glyphs, with the rating as their VoiceOver label. The title is the row's name; a row with no matches shows "No Flagged Photos" and the like.
- A saved folder that is `missing` is dimmed and has a Locate… button that relinks it through `FileAccess`. One that is `offline` is dimmed without the button. Removing a folder asks first and says that photos and edits are not deleted.
- The window is in one of two modes, Browse or Edit, held in `BrowseState` together with the selected photo. Photos are identified by a `PhotoReference`, their folder and file name, so photos with the same name in different folders are told apart; `ListedPhoto` pairs a photo with its folder for the grid and the filmstrip. Both modes follow the system's light or dark appearance. Browse shows the sidebar and a thumbnail grid of the selected folder. While a folder or All Photos is selected, a filter button in the toolbar opens a menu that narrows it (`FilterCriteria`): Clear Filter, then a Flag section (Any Flag, Flagged, Unflagged, Rejected), a Rating section (Any Rating, 5 to 1 stars) with Include Higher Ratings, and an Edits section (Edited or Not, Edited, Unedited). The parts combine: each one set must match. While a filter is on, the button shows how many parts are set, from 1 to 3; its tooltip and VoiceOver label name them, such as "Flagged · 4+ Stars". A rating leaves rejected photos out unless the flag is Rejected. The grid's top edge is the hard scroll edge style, so the title bar has the same fill and dividing line over the grid as over an empty view, and photos scrolled under it are blurred. The title is the folder name and the subtitle its photo count, or "12 of 120 photos" while filtered. A photo counts as edited when its `.proof` sidecar exists. A star filter shows photos with exactly that rating in XMP that aren't rejected. `FolderContents.read` reads XMP sidecars while listing the folder; for photos without one, `Library` reads the XMP embedded in each photo of the selected folder, or of All Photos, in the background, so those photos join the filter as they are read. `PhotoMetadata` holds the rating, the flag (unflagged, flagged or rejected) and the label; see [decision 0005](decisions/0005-reading-xmp.md) for how each app's XMP is read.
- The grid shows each thumbnail as soon as `ThumbnailCache` delivers it, so a folder on a NAS fills in while it is read. Thumbnails are loaded for every photo in the folder, so changing the filter doesn't read it again. When more photos are listed, such as when All Photos reads another folder, thumbnails already shown are kept. Click selects a photo and the arrow keys move the selection; Esc deselects every photo. Double-click or Return enters Edit. A photo the filter hides is deselected.
- Several photos can be selected in the grid and the filmstrip, as in Finder: ⌘-click adds or removes a photo, ⇧-click selects the range from the last photo clicked, Edit › Select All (⌘A) selects every photo that passes the filter, and Deselect All (⌥⌘A) clears the selection, or in Edit keeps only the photo shown. `BrowseState` holds the set, `selectedPhotos`, and the one photo Edit shows, `selectedPhoto`; adding photos keeps it, so the photo in Edit doesn't change while photos are added from the filmstrip. A plain click and the arrow keys select a single photo again. Every selected photo has the same outline. While more than one is selected, the subtitle ends with the count ("12 selected"). Actions on the selection are in the menu bar and the right-click menu, never the toolbar, so there is room for more of them: the menu bar's Rating and Flag (and their keys), Copy Settings…, Paste Settings and Revert to Original act on every selected photo, and their checkmarks show a rating or flag the photos share. The toolbar's stars and flags in Edit rate only the photo shown. Right-clicking a photo in the grid or the filmstrip (`PhotoContextMenu`) shows Edit and Show Info or Hide Info (in the grid), Rating and Flag submenus, Show in Finder, Copy Path, Copy Settings…, Paste Settings and Revert to Original. Show in Finder opens a Finder window with the originals selected; Copy Path puts their paths on the pasteboard, one per line. Right-clicking a folder in the sidebar shows Show in Finder, Copy Path and Refresh, which reads that folder and its subfolders again; saved folders also have Remove Folder…, and missing ones Locate…. As in Finder, it acts on the whole selection when the photo clicked is part of it, and on that photo alone otherwise; Copy Settings… copies from the photo clicked. Reverting more than one asks first, since some may be out of sight. VoiceOver marks each selected photo and offers Add to Selection or Remove from Selection.
- Edit hides the sidebar, restoring it on return. The title is the photo name and the subtitle the folder and the photo's position among the photos that pass the filter ("3 of 120"). The toolbar has a back button at the leading end, in one group with the filter and filmstrip buttons, and at the trailing end the stars and the flags, as two groups, then the crop button and the inspector button, each a group of its own; the title stands on its own beside the back button. The back button and Photo › Back to Folder (⌘↑) return to Browse with the same photo selected. Esc never leaves Edit; it only closes tools, such as the crop tool, the eyedropper and the guides. Backslash (Photo › Show Original) switches the canvas between the edited photo and the original, with no adjustments but the same crop, turns and flips, so both frame the same picture; the subtitle starts with "Original" while it shows, and the histogram measures what the canvas shows. Only the view changes. Leaving the photo or Edit, any change to the edit (including undo, Revert and a card's switch), and opening the crop tool or the eyedropper show the edited photo again, so no change is made out of sight. `BrowseState` holds it, so it ends with the photo. While cropping, Cancel and Done take the crop button's place. The adjustments sit in an `.inspector` panel beside the photo and show the photo's saved edit. White Balance has a preset menu (As Shot, Auto, Daylight, Cloudy, Shade, Tungsten, Fluorescent, Flash, and Custom once a slider has moved or the eyedropper has picked) with an eyedropper button to its right, Temperature in Kelvin and Tint. The eyedropper (W) turns the pointer into a crosshair with a loupe beside it, showing the pixels under it and the center one's red, green and blue; a click on something neutral sets Temperature and Tint so it is gray, as one undo step, and closes the eyedropper. Esc closes it without a pick. The button is inverted while it is open. Basic follows Lightroom's Basic panel: Exposure, Contrast, Highlights, Shadows, Whites and Blacks under a Tone heading, then Texture, Clarity and Dehaze under a Presence heading. Detail groups its sliders as Lightroom's Detail panel does: Amount under a Sharpening heading, and Luminance, Detail and Color under a Noise Reduction heading. Detail, how much fine detail luminance noise reduction keeps, is dimmed while Luminance is 0, because it has no effect then. VoiceOver reads each slider's full name, such as Noise Reduction Detail. Each value can be typed, and Up and Down arrows step it, by more with Shift and by less with Option. Double-clicking an adjustment's name or its slider resets it. Each group is a card with its title inside and, on the right, Reset and a switch (decision 0015). The switch turns the group's adjustments on or off and opens or closes its card; off shows the photo without them, to compare, and isn't saved. When a photo opens, White Balance, Basic and Color are on, and Curve, Detail, Transform, Effects and Looks are off unless the photo has a curve, changed sharpening or noise reduction, a perspective correction, an effect or a look. Effects follows Lightroom's Effects panel: a Vignette heading over Amount, Midpoint, Roundness and Feather, then Grain (Amount, Size, Roughness), Halation (Amount, Size) and Bloom (Amount, Size). Each section's other sliders are dimmed while its Amount is 0. The White Balance preset and the Looks folder are full-width pop-up buttons, as in Finder's settings. Each slider's track shows what it does to the photo, as in Lightroom: Temperature runs blue to yellow and Tint green to magenta, each color fading toward a light middle rather than blending through gray, Exposure runs black to white, Highlights gray to white and Shadows black to gray. Texture, Clarity and Dehaze run light to dark, the reverse of the tone sliders. These tracks and the histogram are the only color in the interface. The Temperature slider is spaced evenly in mireds (a million divided by the Kelvin), so the common range of 2000–10000 K takes most of its length.
- Crop (C, or the toolbar's crop button) opens the crop tool. The inspector shows the crop controls in place of the adjustments, and the canvas shows the whole photo, turned and flipped, with the crop rectangle drawn over it and the photo outside it faded toward the canvas. The rectangle's corners and edges are dragged to resize it and its inside to move it; a rule-of-thirds grid shows while dragging, and a finer grid while straightening. The rectangle always lies on the photo: a drag stops at its edges, and straightening shrinks the rectangle around its center just enough. The tool keeps the rectangle from before straightening, so it grows back as the angle returns to zero. The canvas tilts the photo as it draws it rather than rendering again, so straightening follows the slider without waiting. Each control in the Crop card has its name above it, as the sliders do. The card has the aspect ratio pop-up (Freeform, Original, 1:1, 4:5, 5:7, 3:2, 16:9, Custom, where Custom takes a typed ratio), Swap (X) for landscape or portrait, Straighten from −45° to 45°, and Level. Level's Draw Line button, which reads Done while drawing as Draw Guides does, turns drags on the photo into a line, and the photo straightens so that line is level, or upright when it is drawn closer to vertical. The line stays on the photo while the ruler is on, with a hollow ring at each end, as the Transform guides have; dragging an end turns the photo as it goes, so the line becomes level again; dragging the line moves all of it onto something else without turning the photo, as a guide's line does; and a drag anywhere else draws a new line. While the ruler is on, a pill at the top of the photo, the same one the guides have, leads with what to do, then Clear, which removes the line and keeps the angle, and Done, which turns the ruler off. Return and Esc are Done too, rather than closing the crop tool. The line is kept on the photo rather than the screen (`LevelLine`), so it stays on what it was drawn along as the photo turns. Turning the ruler off, closing the tool, or a quarter turn or flip removes it. Its Auto button renders the photo, turned and flipped but not straightened, at about 1024 pixels and asks Vision (`DetectHorizonRequest`) for the horizon; when Vision finds none, the angle stays as it was and No horizon found shows beside Level's name for two seconds. Dragging just outside a corner of the rectangle also straightens: the photo turns with the pointer around the rectangle's center. Both set the same angle as the slider, within its range; the math is in `ProofKit` (`Horizon`). Below them, Rotate and Flip has a quarter turn each way and a flip each way. The card has Reset, which resets the rectangle, the turn and the flips, and no switch: the tool already shows the whole photo, and Done or Cancel is the comparison. The photo keeps the canvas's usual 24 pt margin while cropping, so it doesn't shrink when the tool opens; the handles are drawn inside the crop border. The ratio starts at Original for a photo without a crop. A preset takes the current rectangle's orientation. Done (Return) keeps the crop, and Cancel (Esc) returns to the edit from when the tool opened, as one undo step. Leaving the photo any other way keeps the crop. The geometry is computed in `ProofKit` (`Crop` and `CropFrame`), so it is tested without the app.
- The Transform card, below Lens Corrections, follows Lightroom's Geometry panel. Its Upright pop-up, with its name above it, lists Off, then Auto and Guided, then Level, Vertical and Full. While Upright looks for lines, a spinner and Finding lines… show on the name's line, and No straight lines found shows there for two seconds when it finds none, so nothing below moves. The pop-up shows the chosen mode at once, and keeps it when no lines are found, with nothing corrected. Upright sets Vertical, Horizontal and Rotate, which stay editable, and returns the crop's straighten angle to zero; choosing the same mode again undoes changes made to them by hand. Off returns them to zero. Constrain Crop, on by default, sits under Upright, as in Lightroom Classic, and keeps the corrected photo filling the frame. Aspect, Scale, X Offset and Y Offset sit in a disclosure group, closed unless the photo uses them. With Guided chosen, one full-width button under the pop-up reads Draw Guides (Edit Guides once there are some) and Done while drawing. Guided keeps the photo as it was, cropped and zoomed, so opening it moves nothing; guides are mapped through the crop (`Crop.photoPoint` and `resultPoint`) to the uncropped photo they are stored on. Each drag on the photo draws a guide along an edge that should be upright or level. Dragging a guide's end moves that end, and dragging its line moves the whole guide; the photo is corrected when the drag ends, with the guides drawn where they now fall. A guide's ends are hollow rings, filled while the pointer is on one or it is held, and when it or its line was clicked last; that guide is the one Delete removes. A fifth guide replaces the oldest. A pill at the top of the photo leads with what to do, then the guide count, with Clear All and Done as capsule buttons; Return and Esc are Done too. The square grid shows while a slider is dragged, as for Distortion. The card starts off unless the photo has a correction (decision 0025).
- A red, green and blue histogram is the inspector's first card, Histogram, which has no Reset or switch. Each channel is a see-through fill with a solid outline, so every channel's shape stays readable where they overlap. In the dark appearance the fills add like light, so where all three overlap they show as gray; in the light appearance they are layered, because adding them on a light card would wash them out. Below the graph, the card shows the photo's ISO, focal length, aperture and shutter speed, read from its EXIF when it opens in Edit (`CaptureSettings` in `ProofKit`); any the photo doesn't record are left out. It counts the render the canvas shows, at screen size, with `CIAreaHistogram` in Display P3, the encoded values on screen rather than linear light. Its height is scaled to the tallest bin other than pure black and pure white, so clipped shadows or highlights show as a spike at the edge without flattening the rest. The canvas measures each finished render beside its render loop, not in it, so a slider drag never waits for the histogram; like renders, one measurement runs at a time and the next takes the latest photo shown. A measurement of a 2560×1600 render takes about 6 ms (median) on an M2. VoiceOver reads the share of clipped shadows and highlights.
- A filmstrip runs under the photo in Edit, one row of thumbnails of the photos that pass the filter, from the same `ThumbnailCache`. It sits in a rounded card with the inspector cards' gray, 24 pt from the window's edges. The card holds only thumbnails. The toolbar's filmstrip button, or View › Hide Filmstrip (⌥⌘F), hides the card; the photo grows into the space, and the choice is remembered across launches. The current photo has the selection outline and is scrolled to the middle. Click or the left and right arrow keys switch photos without leaving Edit; the arrows stop at the first and last photo. ⌘-click and ⇧-click select more photos, outlined, without changing the photo shown. Edit's toolbar has the same filter button as Browse, beside the filmstrip button, and it changes the same filter, so filtering in either mode narrows both the grid and the filmstrip (#160). While a sidebar filter row is selected, there is no filter button, as in Browse. Changing the filter in Edit keeps the photo shown on the canvas even if it doesn't match. When no photo matches, the card shows only a centered message, with Clear Filter under it unless a sidebar filter row is selected.
- Zoom is in the View menu: Zoom In (⌘+), Zoom Out (⌘−), Zoom to Fit (⌘0) and Actual Size (⌘1, 100%). Zoom In and Zoom Out step through Fit, 25%, 50%, 100%, 200% and 400%, with Fit wherever it falls for the photo and the window. The toolbar shows the current zoom as a pop-up of the same steps. Pinching and ⌘-scrolling zoom around the pointer, from 25% to 400%; scrolling or dragging pans, with an open hand as the pointer, and the photo stops at its edges. Double-clicking zooms from Fit to 100% at the clicked point and from any other zoom back to Fit. While the photo is larger than the view, a navigator shows in the canvas's top-right corner, under the zoom pop-up, as in Lightroom: a copy of the whole photo, 160 points on its long edge, with a box around the part in view. It sits in the selection outline, filled with the canvas gray, so it reads as a frame over the photo. It has a square, one-point edge in the canvas gray. Clicking or dragging on it centers the view there. It is a temporary tool, so it sits on the photo, and it fades away at Fit. Its image is made from each screen-size render beside the histogram, so it never delays the canvas. Each photo opens at Fit. The crop tool shows the whole photo, so it opens at Fit and zoom is off while it is open.
- The canvas in Edit is white in the light appearance and 13% gray in the dark, so the whole window changes with the system. It runs under the toolbar glass and stops at the inspector, which has the same plain color instead of its usual material, so the photo and its panel read as one surface. The sidebar and the Browse area use the same color, so the whole window is one surface in either mode. The toolbar uses the system's default background and scroll edge effect: content that scrolls under it, such as the grid's thumbnails, is blurred behind the toolbar material, so the title and subtitle stay readable. Proof doesn't hide or restyle the toolbar background. The photo is centered with a margin and stays inside the safe area.
- Proof's own interface uses only black, white and gray, so no color competes with the photo. The app's accent color is black in the light appearance and 40% gray in the dark; it colors the focused sidebar selection and the slider. White would make the selected row's text unreadable, because macOS keeps that text white. A selected thumbnail in the grid, the filmstrip or the Looks card has a selection outline: a 1 pt rounded line a few points outside the photo, light gray in light and white in dark, with no fill. In the grid, the photo's name sits inside the outline, under the photo. Thumbnails have 4 pt corners, and the outline's corners are that plus the padding, so the two stay concentric. Only the selected thumbnail has an outline; the padding is kept on the others so selecting one moves nothing. Folder symbols in the sidebar are gray. macOS uses an app's accent color only when the system accent is Multicolor; with another system accent, that color shows instead.
- Thumbnails in the grid and the filmstrip show what other apps recorded in XMP: a flag in the photo's top-right corner if it is flagged, and the rating as a star and a number in its bottom-left, in white on a dark backing. Unflagged and unrated photos show nothing. A photo with an edit shows a pencil in its top-left corner in the same style; it is the photo the Edited filter matches. A rejected photo has no flag badge and is dimmed to 35% opacity, as in Lightroom. VoiceOver reads the rating, the flag and "edited" after the photo's name. The grid shows each photo's file name centered under it; photos sit on the bottom of their square so the name is directly under every photo.
- In Edit, the toolbar has two groups of buttons: five stars, and Flagged, Unflagged and Rejected. Clicking a star sets the rating and clicking the current one clears it; the current flag is shown selected. The flag icons follow Lightroom: a filled flag, an outlined flag, and a filled flag with an X cut out of it (SF Symbols has no such symbol). The Photo menu has the same choices with Lightroom's keys: 0 to 5 for stars, P, U and X for the flag, in Browse and Edit.
- A changed rating or flag is saved to the photo's XMP sidecar by `XMPSidecar`, off the main thread, creating `IMG_0001.xmp` when there is none. Only `xmp:Rating`, `xmpDM:pick` and `xmpDM:good` change; the rest of the file keeps its bytes. See [decision 0022](decisions/0022-writing-ratings.md). In a folder with a read-only grant, Proof asks for access once; until then the change stays in memory, the Edit inspector says it isn't saved, and it is saved once the folder is granted. When a folder is read again, a changed rating stays unless the photo's XMP sidecar has one; XMP read from inside a photo is kept the same way. A photo whose rating or flag changed stays visible until the filter or folder changes, even if the filter no longer matches it; in Edit, only until another photo is shown. XMP read in the background never replaces a rating already changed.

While cropping, Photo has Done Cropping (Return), Cancel Cropping (Esc) and Swap Crop Orientation (X) in place of Crop, and X no longer rejects the photo.
- The sidebar selection, All Photos, a filter row or a folder's `FileReference`, is remembered between launches. A selection saved before All Photos existed is still read. The selected photo is not remembered.

- View › Show Info (⌘I) shows the Info panel in the inspector column (`InfoInspector`), as does Show Info in a photo's right-click menu, which selects only that photo first. While the panel is open, a button in the toolbar with the same symbol as the inspector button in Edit hides it; there is no toolbar button to open it. When the panel opens or closes, the grid lays out at once for the width it will have, from the panel's last width, so the photos keep one size and move to their new places while the panel slides. It describes the one selected photo and follows the selection; with several selected it shows none. In Edit, the same details are in an Info card below the histogram, collapsed until opened, and ⌘I opens and closes it. File and capture details are read-only, from `PhotoInfo`. Title, caption, keywords, creator, copyright and location come from `PhotoDescription` and are saved to the XMP sidecar by `XMPSidecar` when a field is left, after any rating still being written. ## Folder access

`FileAccess` in `ProofKit` is the only code that creates or resolves bookmarks. It hides how a folder was granted: on the Mac it stores a read-write security-scoped bookmark; on iOS, a `BookmarkSystem` for folders picked in the Files app can take its place. Saved locations are kept as JSON in Application Support.

- Access to a folder covers every file and subfolder inside it. Adding a folder that is already saved, or sits inside a saved folder, returns the existing location. When saved folders are nested, a file belongs to the innermost one.
- Other code refers to a file as a `FileReference`: a location's identifier plus a path relative to it. A location keeps its identifier when it moves or is relinked, so references stay valid.
- When a location is resolved, a folder moved or renamed on the same volume is followed and a stale bookmark is replaced.
- A location that can't be resolved is kept. It is `offline` when its volume, such as a NAS share, isn't mounted; bookmarks are resolved without mounting so launch doesn't wait on the network. Otherwise it is `missing` and can be relinked to another folder.
- Proof writes only its own sidecars next to photos, never the photos themselves. Folders added or relinked now get read-write grants. Folders saved before that keep their read-only grant and `canWrite` is false; they stay browsable, and the first time Proof needs to write into one, `Library.ensureCanWrite(nextTo:)` opens the folder picker at that folder with Grant Access. `FileAccess.grantWriteAccess` accepts only that same folder (decision 0007). A location that is a single photo, saved by an early build, can't hold a sidecar, because the sandbox allows writing beside a file only through a grant to its folder. Proof asks for that folder in the same way, and the location becomes the folder, keeping its identifier (decision 0008).
- Removing a location forgets its grant. Photos, sidecars and edits on disk are not touched. Network shares are treated as slow: thumbnails come from the RAW file's embedded preview and are cached locally, and folders on network volumes are rescanned on demand instead of watched.
- Folders change without a relaunch. `FolderWatcher` in `ProofKit` watches the available saved folders on local disks with FSEvents, so local disks are never polled; a folder that changed is read again if it had been read. FSEvents doesn't report changes another computer makes on a network volume, so folders there are read again when Proof becomes the active app, and every read folder is read again with View › Reload Folders (⌘R).
- When a drive or network share connects or disconnects, `Library` asks `FileAccess.recheck` for each location's status. A folder that becomes available is read and fills the sidebar, and All Photos reads it and stops naming it in the subtitle. One whose volume went away is `offline`, and what was read of it is forgotten so it is read fresh when it returns.
